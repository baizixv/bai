# 项目维护规范

本文档记录白子诩数字花园的工程约定。目标不是追求形式上的复杂，而是让新增内容、页面和交互都能被快速定位、独立修改和安全验证。

## 1. 技术边界

- 使用 Astro + TypeScript + Markdown Content Collections。
- 默认输出静态站点，不为本地工具引入后端状态。
- 内容进入 `src/content/entries/`；页面负责组合数据，组件负责展示，脚本负责浏览器交互。
- 浏览器本地数据只能放在 `localStorage`，不得上传用户输入或成绩。
- 外部依赖保持克制：只有在能明显减少重复实现或满足格式/算法需求时才添加。

## 2. 目录职责

```text
src/
├── components/       首页和可复用的 Astro 展示组件
├── content/entries/  文章、项目、工具、游戏、书签和媒体 Markdown
├── data/             稳定的静态配置与测试参考数据
├── lib/              跨功能复用的纯工具，如 storage
├── layouts/          页面骨架、全局导航和 meta
├── pages/            路由入口；尽量只做数据查询和组件编排
├── scripts/          绑定具体页面 DOM 的浏览器交互
│   └── benchmark/    按测试类型拆分的人类基准测试实现
├── styles/           global.css 入口和按区域拆分的 CSS modules
└── types/            多个功能共享的 TypeScript 类型
```

`public/` 只放需要原样发布的资源，例如图片、favicon 和 Ogden 词库 JSON；它不是业务逻辑目录。

## 3. 模块化原则

### 单一职责

一个文件、组件或函数只解决一个问题：

- 页面：查询 Content Collection、计算页面所需数据、组合组件。
- 组件：渲染一块完整的界面，不隐式读取另一块页面的 DOM。
- 脚本：管理一个页面或一个独立工具的状态与事件。
- 数据：只保存配置，不在数据文件里编写交互逻辑。
- CSS 模块：按页面区域组织，保持导入顺序与视觉层级一致。

### DRY

- 相同的 localStorage 读写统一使用 `src/lib/storage.ts`。
- 相同的内容筛选、排序和 schema 逻辑优先抽成函数，而不是复制到多个页面。
- 相同的按钮、卡片和颜色使用已有 class；新增样式前先搜索是否已有通用规则。
- 跨页面的类型放在共享类型文件中，避免复制 interface。
- 不为了抽象而抽象：只有出现稳定重复、职责清晰时才提取模块。

### 文件大小

- `src/` 与 `scripts/` 中的 `.astro`、`.ts`、`.css`、`.md` 和 `.mjs` 文件不超过 **300 行**。
- `npm run check:structure` 会自动扫描并在超限时失败；当前检查范围包括 `src/`、`scripts/` 和 `docs/` 中的源文件。
- 文件接近 250 行时就应该考虑按职责拆分，不要等到超过限制。
- 大型数据文件可以保持为数据资源；不要把数据和运行时代码写在同一个脚本里。

## 4. 页面与内容约定

- Markdown frontmatter 必须通过 `src/content/config.ts` 的 schema 校验。
- 新增条目优先使用 Markdown，不在页面中硬编码想法、项目、工具或收藏内容。
- 想法使用 `kind: idea`，进入首页“起一个想法”、想法归档和详情页；可通过 `status` 记录想法萌芽、推敲中、准备实现、实现中或已实现。
- 工具使用 `kind: tool`，通过 `area: tiny` 或 `area: standalone` 进入对应区域。
- 媒体使用 `kind: media`，通过 `mediaType: book | screen | music | game` 分类；书名统一用中文书名号展示，书籍可填写 `wordCount`，并使用 `color` 为不同条目分配视觉主题。
- 详情页按钮统一放入 `.detail-actions`，**本站体验在前，外部项目在后**。
- 外部链接必须明显可识别，使用外链图标或颜色，并在新标签页打开。
- 首页内容区使用集合数据计算统计，禁止恢复硬编码的项目数量或更新时间。
- 响应式样式与桌面样式一起维护在对应 CSS 模块中，移动端不能通过页面脚本补救布局问题。

## 5. 浏览器交互约定

- DOM 查询使用具体的元素类型泛型，例如 `querySelector<HTMLInputElement>`。
- 事件监听必须在脚本自身负责的页面范围内绑定；动态列表优先使用事件委托。
- 异步操作要有失败状态，不能让网络或 JSON 数据加载异常变成空白页面。
- 定时器、动画帧和全局事件必须在页面切换或测试重启时清理。
- 用户输入进入 `innerHTML` 前必须转义；能使用 DOM API 时优先使用 DOM API。
- 每个功能的键名集中管理，避免 localStorage key 在多个位置散落。

## 6. 验证流程

提交前依次执行：

```bash
npm run check:structure
npm run check
npm run build

git diff --check
```

涉及交互时，还要在浏览器中验证桌面端和移动端的主要路径。修改内容 schema、路由、外部链接或工具脚本时，应至少打开对应页面确认实际输出。

## 7. 提交流程

- 一个 commit 尽量只表达一个用户可理解的变更。
- 每完成一个独立、可交付的功能，编码代理应自动执行必要检查；检查通过后自动提交，并立即推送到当前分支对应的远端，无需等待用户再次提醒。
- 提交前检查 `git status` 和 diff，只提交本功能相关文件，不得混入用户已有的无关修改、临时文件、构建产物或敏感信息。
- 检查或推送失败时，保留本地修改或本地 commit，并明确报告失败步骤与原因；不得隐瞒失败或宣称已推送。
- 除非用户明确要求，否则禁止强制推送、改写历史或跳过检查。
- 不提交 `dist/`、临时抓取文件、调试日志或本地环境配置。
- 完成后报告检查结果、commit hash 和推送状态；部署后记录生产地址、构建结果和 commit，方便回溯。
